До разрешения расхождения нельзя фиксировать финальную Supabase schema и backend parity как завершённые.

## Архитектурные инварианты

- Favorite — пользовательская редактируемая текущая проекция.
- LIVE/Deal цены не перезаписывают ручную Favorite-цену.
- Events LIVE — системная read-only проекция.
- Series и Occurrence — разные сущности.
- Прошедшее Event не создаёт Visit автоматически.
- Research становится Favorite только после реального положительного Visit.
- Негатив локализуется на минимально обоснованном уровне: place/provider/config/mechanism.
- History / evidence не уничтожается новыми фактами.
- Visit хранит отдельно activity/event, public transport, taxi, road total, visit total.
- Blank = неизвестно; 0 = подтверждённо отсутствовал расход.
- Posting по VisitID/TxID идемпотентен.
- Monthly budget версионируется по effective month и не переписывает закрытые месяцы.
- Carryover переносит знак полностью, включая отрицательные значения.
- Refund/correction — отдельная signed append-only транзакция.
- Reserved/payment due — обязательство, не расход.
- Paid — реальный cash flow.
- Supabase должен использовать нормальные сущности, FK/constraints/transactions, а не один JSON blob как основную модель.

### Новые пользовательские требования к дашборду — 25.09.2026

- Принять текущую светлую трёхколоночную dashboard-концепцию как базовое визуальное направление.
- Убрать отдельный блок «Быстрый выбор»: его место отдаётся расширенной погоде и полезному контенту.
- Погодный блок должен показывать:
  - **сегодня** — 4 периода: утро / день / вечер / ночь;
  - **неделю** — краткий прогноз на 7 дней;
  - температуру, погодное состояние и осадки/иконку минимум.
- Погода является пользовательским контекстом выбора. На первом этапе она не обязана автоматически менять выдачу, но данные должны быть доступны UI и дальнейшей рекомендательной логике.
- Блок Research на Главной увеличить относительно раннего макета: он не должен выглядеть второстепенным. На desktop показывать ориентировочно 5–6 Research-позиций или эквивалентный полезный объём с внутренним скроллом/«Показать все».
- Favorite / Research / Event должны поддерживать **обложку / изображение**:
  - у записи предусматривается стабильное поле cover/image;
  - при отсутствии изображения используется единый fallback;
  - сломанная внешняя картинка не должна ломать карточку;
  - источник изображения и право/допустимость его использования должны учитываться при ingestion.
- На компактных карточках Favorite / Research / Event обязательно показывать временные параметры:
  - длительность самого опыта;
  - время дороги;
  - полное время, если оно рассчитано.
- Время не объединять в одно неоднозначное поле: пользователь должен понимать, где «на месте», где «дорога», где «всего».
- Events продолжают показывать дату и время начала/окончания, если они известны.
- Картинки являются частью карточки, но не должны снижать плотность дашборда: фиксированный thumbnail/cover aspect-ratio и lazy loading.
- Для погоды и внешних медиа нельзя помещать секретные API-ключи во frontend. Если выбранный провайдер требует secret key, запрос должен идти через backend/Supabase Edge Function либо другой защищённый слой.
- Не вводить отдельное визуальное «усиление главного тезиса» для карточек Favorite: карточки остаются ровными и информативными, без дополнительной рекламной плашки вроде «лучше вечером / для двоих / быстро добраться» как обязательного элемента.
- Сортировка, поиск и фильтрация должны одинаково хорошо работать для **Favorite / Куда сходить** и **Research / Исследовать**.
- Пользователь должен уметь искать и фильтровать не только по названию/цене/району, но и по **эмоциям / состояниям** и **атрибутам атмосферы**.
- Атрибуты атмосферы должны использовать существующую предметную модель и профиль восприятия (например: вода, простор, тишина/спокойствие, вечерние огни/подсветка, зелень, музыка, фонтаны, архитектурная выразительность и другие уже заведённые атрибуты), без создания дублирующей параллельной классификации.
- В полной выдаче эмоциональные и атмосферные поля должны быть доступны как включаемые колонки и как фильтры; если конкретное поле является числовой шкалой, по нему должна работать сортировка по возрастанию/убыванию.
- Для текстовых/теговых атмосферных атрибутов использовать фильтрацию/поиск и, где это осмысленно, алфавитную сортировку по представлению; не придумывать искусственный числовой рейтинг атмосферы без данных.
- Events участвуют в эмоционально-атмосферном поиске только если соответствующие атрибуты реально есть в нормализованных данных события; отсутствующие значения не заполнять догадками.
