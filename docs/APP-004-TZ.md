## Архитектурные инварианты

- Favorite — пользовательская редактируемая текущая проекция.
- LIVE/Deal цены не перезаписывают ручную Favorite-цену.
- Events LIVE — системная read-only проекция.
- Series и Occurrence — разные сущности.
- Прошедшее Event не создаёт Visit автоматически.
- Research становится Favorite только после реального положительного Visit.
- Негатив локализуется на минимально обоснованном уровне: place/provider/config/mechanism.
- History / evidence не уничтожается новыми фактами.
- Visit хранит отдельно activity/event, public transport, taxi, road total, visit total.
- Blank = неизвестно; 0 = подтверждённо отсутствовал расход.
- Posting по VisitID/TxID идемпотентен.
- Monthly budget версионируется по effective month и не переписывает закрытые месяцы.
- Carryover переносит знак полностью, включая отрицательные значения.
- Refund/correction — отдельная signed append-only транзакция.
- Reserved/payment due — обязательство, не расход.
- Paid — реальный cash flow.
- Supabase должен использовать нормальные сущности, FK/constraints/transactions, а не один JSON blob как основную модель.

  - у записи предусматривается стабильное поле cover/image;
  - при отсутствии изображения используется единый fallback;
  - сломанная внешняя картинка не должна ломать карточку;
  - источник изображения и право/допустимость его использования должны учитываться при ingestion.

  - длительность самого опыта;
  - время дороги;
  - полное время, если оно рассчитано.
- Время не объединять в одно неоднозначное поле: пользователь должен понимать, где «на месте», где «дорога», где «всего».

- Картинки являются частью карточки, но не должны снижать плотность дашборда: фиксированный thumbnail/cover aspect-ratio и lazy loading.
- Для погоды и внешних медиа нельзя помещать секретные API-ключи во frontend. Если выбранный провайдер требует secret key, запрос должен идти через backend/Supabase Edge Function либо другой защищённый слой.
- Не вводить отдельное визуальное «усиление главного тезиса» для карточек Favorite: карточки остаются ровными и информативными, без дополнительной рекламной плашки вроде «лучше вечером / для двоих / быстро добраться» как обязательного элемента.
- Сортировка, поиск и фильтрация должны одинаково хорошо работать для **Favorite / Куда сходить** и **Research / Исследовать**.
- Пользователь должен уметь искать и фильтровать не только по названию/цене/району, но и по **эмоциям / состояниям** и **атрибутам атмосферы**.
- Атрибуты атмосферы должны использовать существующую предметную модель и профиль восприятия (например: вода, простор, тишина/спокойствие, вечерние огни/подсветка, зелень, музыка, фонтаны, архитектурная выразительность и другие уже заведённые атрибуты), без создания дублирующей параллельной классификации.
- В полной выдаче эмоциональные и атмосферные поля должны быть доступны как включаемые колонки и как фильтры; если конкретное поле является числовой шкалой, по нему должна работать сортировка по возрастанию/убыванию.
- Для текстовых/теговых атмосферных атрибутов использовать фильтрацию/поиск и, где это осмысленно, алфавитную сортировку по представлению; не придумывать искусственный числовой рейтинг атмосферы без данных.
- Events участвуют в эмоционально-атмосферном поиске только если соответствующие атрибуты реально есть в нормализованных данных события; отсутствующие значения не заполнять догадками.

Search / Results **не является отдельной вкладкой верхней навигации**.

- после ввода/отправки запроса в глобальном поиске;

# 28. User Acceptance Corrections — 26.09.2026

Этот раздел фиксирует реальные замечания после первого пользовательского прохода по live v0.4 и **имеет приоритет над более ранними противоречащими UI-правилами**.

## 28.1 Настройки

- Блок **«Поддержка» удалить полностью** из Settings.
- Справа остаются только пользовательские блоки: Account / My Data / About и другие реально нужные секции.
- Поле месячного бюджета обязано **реально сохраняться** и переживать F5 / повторный вход.
- У бюджета должна быть понятная точка фиксации: отдельная кнопка **«Сохранить бюджет»** рядом с полем либо гарантированное autosave. Для release выбрать явный save как более проверяемый вариант.
- После сохранения показывать результат: успешно / ошибка. Silent failure запрещён.
- Кнопка общего «Сохранить настройки» не должна создавать лишнюю budget-version, если сумма бюджета не изменилась.
- «Восстановить стандартные настройки» оставить: в пользовательском тесте работает.
- **Экспорт данных — release blocker**: по нажатию должен реально формироваться и скачиваться пользовательский файл. Нельзя показывать успешное состояние, если файл не создан.
- Все переключатели/селекты Settings должны иметь проверяемый эффект в runtime, а не быть декоративными.
- «Период событий» должен реально управлять live-окном событий на Dashboard/Search. Значение 14 дней не должно быть hard-coded отдельно от Settings.

## 28.2 Текущая дата и окно Events LIVE

- На Главной явно показывать текущую московскую дату, например: **«Сегодня, 26 сентября»**.
- Временная зона для правил Dashboard/Events: **Europe/Moscow**.
- События на Dashboard и в активной Search-выдаче должны очищаться относительно сегодняшней даты автоматически.
- Датированное событие считается актуальным:
  - если есть `ends_at` — пока `ends_at >= начало текущего дня по Москве`;
  - если `ends_at` нет — пока `starts_at >= начало текущего дня по Москве`.
- Событие 23 сентября не должно оставаться в live-выдаче 26 сентября, если оно уже завершилось.
- Верхняя граница live-окна берётся из Settings (`event_horizon_days`), по умолчанию 14 дней.
- Старые Event Occurrence **не удалять физически из доказательной базы**. Они должны автоматически исчезать из LIVE projection / Dashboard / актуального Search, сохраняясь для истории, аудита и возможной связи с Visit.
- Для on-demand / «по записи» события нужен отдельный валидный срок (`valid_until`, `fresh_until` или эквивалентный канонический факт). Если срок неизвестен/просрочен — не держать запись бесконечно в LIVE.

## 28.3 Погода

- Погода не декоративная: данные должны приходить из реального runtime-источника.
- Базовый провайдер v0.4: Open-Meteo.
- Settings → «Город» должен реально менять город погодного запроса.
- Settings → «Показывать погоду» реально скрывает/показывает блок.
- Settings → «Прогноз на 7 дней» реально скрывает/показывает недельный блок.
- На Главной обязательно:
  - сегодня: утро / день / вечер / ночь;
  - 7 календарных дней: дата/день недели, min/max, состояние, осадки.
- `NaN`, пустая температура или фиктивный прогноз недопустимы. При ошибке провайдера показать понятное «Погода временно недоступна», а не ложные значения.
- Перед release проверить фактический ответ провайдера и отображение всех 7 дней в браузере.

## 28.4 Навигация: Search становится отдельной верхней страницей

Новое правило **заменяет прежнее правило «Search / Results не является отдельной вкладкой»**.

Верхняя навигация:
**Главная / Поиск / История / Настройки**.

- **Поиск** — самостоятельная страница полного поиска и расширенных фильтров.
- Dashboard быстрые фильтры работают **на самой Главной** и не должны автоматически переводить пользователя в Search.
- Кнопка **«Ещё фильтры»** на Главной открывает страницу Поиск и переносит туда текущий контекст/быстрые фильтры.
- Глобальный поиск на Главной может открывать Поиск с введённым запросом.

## 28.6 Избранные события

## 28.7 Карта

### Search map

### Detail map

- Координаты брать из `app004_places.latitude / longitude`; Research/Event/Experience получают координаты через `place_id`.
- Если координат нет — не рисовать фиктивный pin; показывать понятное состояние «Координаты пока не определены» и запускать geocoding/backfill.

### Обязательный data-fix
На 26.09.2026 структура координат существует, но текущий импорт не заполнил координаты Places. Перед запуском карты нужен одноразовый/инкрементальный geocoding по подтверждённому адресу/названию/официальной локации с сохранением lat/lon в Places.

## 28.10 GPT Active Task → Events runtime

Поиск новых событий может продолжать работать отдельной активной задачей GPT.

Целевой результат:
- GPT собирает/проверяет Event;
- сохраняет данные в каноническую staging-таблицу/Excel;
- runtime APP-004 получает тот же Event без ручного переписывания.

Предпочтительный путь:
1. Excel/Sheet остаётся понятным staging/master-контуром для проверки.
2. Для runtime сделать idempotent Event ingestion/upsert в Supabase по стабильному ключу события/occurrence.
3. Если активная GPT-задача может вызывать Supabase ingestion — использовать dual-write: Excel + Supabase.
4. Если прямой Supabase write из активной задачи недоступен — использовать bridge:
   - отдельный Google Sheet Events LIVE;
   - задача пишет туда;
   - sync-job импортирует Sheet → Supabase;
   - GitHub Pages читает только Supabase.
5. Не заставлять браузер парсить приватный .xlsx как основной production runtime.

Ingestion обязан:
- upsert, а не плодить дубли;
- обновлять цену/доступность/freshness;
- сохранять source URL и checked_at;
- автоматически переводить просроченные Occurrence из LIVE projection;
- не создавать Visit автоматически.
